## Openstaand — punt 4: Neo4j-wachtwoord roteren

**Correctie op de oorspronkelijke aanname:** authenticatie stond al aan. Een query zonder
credentials geeft `HTTP 401 / No authentication header supplied`, `auth_enabled` staat
uitgecommentarieerd (default = true) en `/data/dbms/auth.ini` bestaat. Dat er geen
wachtwoordprompt verscheen kwam door credential-caching in Neo4j Browser
(`:server disconnect` forceert een prompt).

Wat resteert is **roteren**, omdat het wachtwoord op 2026-08-12 in een chattranscript
zichtbaar is geweest én de database tot die dag vanaf internet bereikbaar was.

1. Via Neo4j Browser (SSH-tunnel, zie onder), in de queryregel:
   ```cypher
   ALTER CURRENT USER SET PASSWORD FROM 'huidig' TO 'nieuw';
   ```
2. `nano ~/pdf-library-web/.env` → `NEO4J_PASSWORD` bijwerken.
3. `cd ~/pdf-library-web && docker compose up -d && docker network connect bridge pdf-library-backend`
4. `nano ~/neo4j/docker-compose.yml` → `NEO4J_AUTH` bijwerken (heeft geen effect op de
   bestaande database, alleen op een toekomstige verse setup). Overweeg de waarde naar een
   `.env` naast de compose te halen.

Daarna verifiëren: kan de indexer nog bij Neo4j met het nieuwe wachtwoord.

## Openstaand — vereenvoudiging ufw

De `docker network connect bridge pdf-library-backend`-stap is een pleister: hij bestaat
alleen om de container een 172.17-adres te geven zodat ufw hem bij poort 11234 laat.
`neo4j_default` is 172.20.0.0/16 en staat niet in de ufw-regels.

Voorstel — vervang de twee subnet-specifieke regels door één:
```bash
sudo ufw allow from 172.16.0.0/12 to any port 11234 proto tcp
sudo ufw delete allow from 172.17.0.0/16 to any port 11234
sudo ufw delete allow from 172.19.0.0/16 to any port 11234
```
Dan is de bridge-koppeling definitief overbodig en is de curator immuun voor
netwerkhernummering (nu breekt LLM-toegang stil als een compose-netwerk hernummerd wordt).

## Openstaand — het eigenlijke geheugenlek

### Drie lekken, alle drie bewezen

1. **Gestapelde pipeline-runs.** `force_stop_pipeline` (`src/web/state.py:166-184`) verwijdert
   het lockbestand, waardoor de knop weer vrijkomt terwijl de oude daemon-thread doorloopt.
   De nieuwe run doet `_clear_cancel()` (`scripts/run_weekly.py:160`) en wist daarmee het
   cancel-signaal van de oude run, die vervolgens gewoon doorgaat.
   *Bewijs:* run 274 (`running`, nooit afgerond) en 275, 4 seconden later gestart.

2. **Geen `try/finally` rond `extractor.close()`** (`scripts/run_weekly.py:254`). Op
   exception-paden en vroege returns wordt hij overgeslagen.

3. **Hoofdoorzaak — `close()` faalt stil.** `sync_playwright().start()` draait in een worker
   van de per-e-mail `ThreadPoolExecutor` (`src/email/extractor.py:660`); die pool wordt per
   e-mail afgebroken, dus de aanmakende thread is dood wanneer `close()` vanaf de hoofdthread
   draait. Playwright's sync-API is thread-affien en gooit; `except Exception: pass`
   (`src/email/extractor.py:710-717`) slikt het.
   *Gereproduceerd in de container:*
   ```
   [threads] created on 'ThreadPoolExecutor-0_0', closing from 'MainThread'
   [close]   RAISED error: cannot switch to a different thread (which happens to have exited)
   ```
   *Gevolg:* elke run die een browser start, lekt hem — ook geslaagde runs.
   *Bewijs:* 5 gelekte Playwright-instanties in de scheduler-container, elk exact
   samenvallend met een Sunday-18:00-run; en run 281 in de web-container is `completed`
   en lekte tóch.

### Bijkomend

- **Zombies.** PID 1 in de container is `uv run reflex run`, geen init. Gekillde of gecrashte
  browsers laten permanente `<defunct>`-slots achter.
- **Drie verschillende lock-implementaties** met afwijkende semantiek:
  `run_weekly.py:100` (mtime, verwijdert stale), `app.py:661` (mtime, verwijdert niet),
  `state.py:85` (alleen bestaan). `LOCK_STALE_SECONDS` is 30 min terwijl runs 50–113 min duren.
- **LLM-clients worden nooit gesloten** (`scorer.py:77`, `exploder.py:261`).

### Fixplan, in volgorde

- **E — GEDAAN 2026-08-13** — `docker-compose.yml`: `init: true`, `mem_limit: 3g`,
  `pids_limit: 512` op web én scheduler.
- **A — GEDAAN 2026-08-13** — Playwright naar één stabiele owner-thread die de hele run leeft en zelf `close()`
  uitvoert; PIDs onthouden als backstop; `except Exception: pass` → `logger.exception`.
  Alléén "één pool voor alle e-mails" is niet voldoende — `close()` komt dan nog steeds van
  de hoofdthread.
  *Implementatie:* `BrowserFetcher` heeft nu een interne `ThreadPoolExecutor(max_workers=1)`;
  `fetch_page`/`resolve_url`/`close` zijn dunne wrappers die het werk daarheen sturen.
  Launch registreert de nieuwe /proc-descendants; faalt of hangt `close()` (60s timeout),
  dan worden die PIDs ge-SIGKILL'd. Ook punt 2 (`try/finally` rond `extractor.close()`)
  is meegenomen, plus de nooit-gesloten scanner-extractor in stap 1b.
  *Geverifieerd lokaal:* fetch vanuit twee opeenvolgende, daarna opgeruimde pools,
  gevolgd door `close()` vanaf MainThread — geen exception, geen achtergebleven
  `headless_shell`-processen; `tests/test_browser.py` 6 passed.
- **C+D — GEDAAN 2026-08-13** — één gedeelde lock-implementatie op PID-liveness (`os.kill(pid, 0)`) in plaats van
  mtime; Force Stop mag het lockbestand niet wissen; `_clear_cancel()` bij runstart weg.
  *Implementatie:* nieuw `src/storage/lock.py`; de drie (feitelijk vier) kopieën in
  `run_weekly.py`, `app.py`, `state.py` en de force-stop-endpoint zijn vervangen.
  Liveness = pid van de eigenaar; op Windows via `OpenProcess`, want `os.kill(pid, 0)`
  dóódt daar het proces. Voor een lock uit een andere PID-namespace (scheduler-container
  deelt `/data`) valt hij terug op een heartbeat: `_write_progress()` ververst de mtime,
  15 minuten stilte telt als dood. Cancel is nu geadresseerd aan één runtoken, dus een
  achtergebleven signaal stopt de vólgende run niet en een nieuwe run wist het signaal
  van een lopende run niet. Force Stop signaleert alleen; de run geeft zijn eigen lock
  vrij. De UI blijft "Stopping — waiting for the current step to finish..." tonen tot
  dat gebeurd is. Gedekt door `tests/test_lock.py` (8 tests).
- **B** — pipeline als subprocess (`start_new_session=True`), PID in het lock, Force Stop via
  `os.killpg`, **en ook bij normale afloop** `killpg` om Chromium-wezen op te ruimen.
  Let op: `start_scheduler()` roept `run_pipeline()` in-process aan, dus B dekt dat pad niet —
  fix A is de enige die álle callers dekt.
- **F — GEDAAN 2026-08-13** — `close()` op de OpenAI-clients in Scorer en Exploder, aangeroepen in een `finally`.
  *Implementatie:* beide klassen hebben nu `close()`; `_run_pipeline_inner` registreert ze
  in een `closers`-lijst en sluit die in een `finally`, zodat vroege returns (LLM
  onbereikbaar, geen items) en excepties de opruiming niet overslaan.
  **Nog te bewijzen:** of dit de +434 MB van run 282 verklaart. Dat blijkt pas uit de
  nameting van de volgende run.

**Afspraak:** E en A samen uitvoeren, dan laten testen vóór C+D.
